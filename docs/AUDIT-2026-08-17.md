# Gridlink Mail interaction audit, 2026-08-17

Driven against a clean-slate install on an Android 16 emulator (`pm clear`, true first-run),
package `app.gridlink` v0.1.0 (versionCode 1000). Every item below was reproduced on-device and
then root-caused in source. Items marked CODE were additionally confirmed by reading the code.

> **Status, updated as the plan is worked.** Items 1, 2, 3, 4 and 7 are FIXED and pushed.
> Item 5 was re-scoped after it turned out to be partly wrong (see below). Item 6 is a design
> call and is Tate's to make. Items 8 and 9 are open. Item 10 stays deferred.
>
> 🔴 **Attribution correction.** Items 3, 5 and 6 name `ConnectScreen.kt`. That is the ADVANCED
> setup screen, reached only by tapping "JMAP, IMAP or Outlook". The screen actually photographed
> at first run is `GridlinkSetupScreen.kt`, reached through `GridlinkSetupHost` (which calls
> `GridlinkApp {` as a trailing lambda, which is why an earlier grep for `GridlinkApp(` missed it).
> The shared button lives in `GridlinkForm.kt`.

## Confirmed defects, ranked

### 1. HIGH / security: the mail password is written into the saved-state Bundle
`ConnectScreen.kt:142` and `:938` hold it as `var password by rememberSaveable { mutableStateOf("") }`.
`rememberSaveable` serialises into the Activity's `onSaveInstanceState` Bundle, which is held by
system_server outside the app process and may be persisted for task restoration. A plaintext mail
credential should never reach it. CODE + reproduced (password restored after forced recreation).
**Fix:** hold the password in the ViewModel (survives config change, never serialised), not in
saveable state.
✅ **FIXED** in `9cbca192`: `ConnectViewModel.PasswordDrafts` holds both the form password and the
per-account import password, cleared once stored. Survives the Fold's hinge, dies with the process.

### 2. HIGH / visual: light mode renders an unreadable status bar
`Theme.kt:56` sets `isAppearanceLightStatusBars = !darkTheme`, so in light mode the status-bar
icons go dark. But the Gridlink-skinned screens are dark-only: `GridlinkSolar.kt` and
`GridlinkTokens.kt` contain zero references to `isSystemInDarkTheme` / `ThemeMode` / `darkTheme`.
Result: dark icons on a dark navy surface, barely legible. The code comment asserts "they stay
legible on the light surface"; on these screens no light surface exists.
**Repro:** `adb shell cmd uimode night no`, open the app, look at the clock. CODE + screenshot.
**Fix:** drive the system-bar appearance from the surface actually being drawn, not from the
Material theme mode.
✅ **FIXED** in `71e4468f`: `AppTheme` stays the single writer of the bar appearance, and
`ProvideGridlinkTokens` publishes the mode it paints into a slot `AppTheme` reads during
composition. Pinned by `SystemBarsAppearanceTest`.

### 3. MEDIUM / accessibility: the disabled Connect button disappears from the a11y tree
With the form empty, Connect is correctly disabled (`ConnectScreen.kt:583`, `enabled = !busy && ready`),
but its clickable node `[1041,2796][1380,2988]` is ABSENT from the uiautomator tree; only a bare
`TextView` reading "Connect" remains, reporting `enabled=true`. A screen-reader user is read static
text with no role and no reason it is unavailable.
**Fix:** keep the button in the semantics tree when disabled and attach a stateDescription saying
what is still required.
✅ **FIXED** in `5f4e599a`. Root cause was `GridlinkConfirmPill` in `GridlinkForm.kt`, which applied
`.clickable` only inside the `if (enabled)` branch, so the Box contributed no semantics node at all
when disabled. `clickable(enabled = false)` keeps the node, publishes the role and marks it
unavailable. The screen's live `hint` now rides along as the pill's `stateDescription`.
`GridlinkTextButton` in `GridlinkSheets.kt` had the identical defect and is fixed with it.

### 4. MEDIUM / UX: notification permission is requested at cold start, and re-requested
The POST_NOTIFICATIONS dialog fires on first launch before any account exists and before the user
has done anything. It fired again after an activity recreation despite an earlier explicit denial.
For a privacy-focused F-Droid audience this is the wrong first impression.
**Fix:** request in context, at the point the user enables push or sync, and never re-prompt after
a denial.
✅ **FIXED** in `d92f640c` and `ee8e7ec2`. The ask moved out of the top of `AppNavHost` into the
`RootState.Authenticated` branch, so it happens once a mailbox exists, and the fact that it was
asked is recorded on disk so a denial is not re-asked every cold start. Because a denial is now
permanent, the notifications settings screen grew a row, shown only while the OS is blocking, that
opens the system notification settings.

### 5. ~~MEDIUM~~ LOW / UX: the empty form is a silent dead end
🔴 **Half of this was wrong and is withdrawn.** "Nothing states what is missing" is not true of the
real first-run screen: `GridlinkSetupScreen.kt:147` computes a live `hint` that names exactly the
next thing needed ("Enter the address you receive mail at, like you@yourdomain.com.", then "Enter
the password, app password or API token for that account."), and `GridlinkFormScreen` renders it.
I mistook that changing hint for a static subtitle.

What survives is the affordance: disabled is drawn as a hairline outline, which is a deliberate
house rule (alpha never encodes state) rather than an oversight, but it reads as chrome rather than
as a button waiting on you. ✅ The accessibility half is closed by item 3, which now speaks the hint
on the button itself. The remaining visual question is folded into item 6, since both are about how
this one screen reads.

### 6. LOW / UX: the optional field leads the required one
The subtitle says "Enter the address you receive mail at", then the first field is SERVER, marked
optional. ACCOUNT (the thing just asked for) is second. The reading order contradicts the instruction.
**Fix:** put ACCOUNT first, SERVER after, or fold SERVER into an "advanced" disclosure.
⏸️ **Tate's call, asked and waiting.** This changes what the first screen of the app looks like,
which is a design decision, not a defect fix. Carries the leftover visual half of item 5.

### 7. LOW: credential restoration is inconsistent
The password survived one forced recreation and was cleared by another (uiMode change). Whatever
the intent, the behaviour is not predictable. Resolving item 1 should make this deterministic.
✅ **CLOSED by item 1.** The lifetime is now stated rather than incidental: the draft lives in the
ViewModel, so it survives every configuration change and no process restart.

## Coverage gaps (from the static audit, unchanged)

### 8. Zero UI / instrumented tests; 28 of 29 screens and view models uncovered
1,622 unit tests pass and the protocol layer is well proven. Nothing covers the layer the user
touches. Every defect above was found by hand in one session because no test could have caught them.

### 9. The phone runs a debug build, so the release path is never exercised
The Fold carries a debug-keystore-signed APK. The minified R8 release build that F-Droid ships is
never run on real hardware. See [[gridlink-mail-audit-2026-08]].

### 10. F-Droid listing is English-only despite 8 translated locales
`fastlane/metadata/android/` holds `en-US` only. DEFERRED: fastlane metadata is read at the tag,
so fixing it means re-tagging, which would move the ground under merge request !46061 while a
maintainer is reviewing it. Do this after the MR merges.

## Verified NOT broken (do not re-audit)

- State survives backgrounding and forced activity recreation, with no crash.
- Connection error copy is clear and actionable ("No JMAP server was found for that address"),
  with Show details / Copy details affordances. Better than most clients.
- The grey floating circle visible in some screenshots is a system overlay, not Gridlink: it has no
  node in the accessibility tree and the only package in the dump is `app.gridlink`.
- Zero crashes across the whole session (`logcat -b crash` clean).
